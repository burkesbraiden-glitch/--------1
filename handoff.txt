# 一、项目一句话定义

**童旅记是一款面向亲子旅行场景的文化研学 App，核心不是“帮用户找旅游景点”，而是让孩子在旅行过程中通过“计划 → 探索任务 → 观察/完成 → 记录 → 回顾”的方式，把一次普通旅游转化为一次有学习成果的亲子文化体验。**

核心理念：

> **旅行不是终点，探索和记录才是学习发生的过程。**

---

# 二、项目最初的产品目标

项目最初是一个“亲子文化旅游指南”方向的 App。

后来逐渐明确：

* 用户主体：家长 + 儿童
* 使用场景：亲子旅游、博物馆、历史文化景点、城市文化探索
* 核心问题：

  * 家长不知道如何让孩子真正参与旅行
  * 孩子到景点后容易变成“看一看、拍一拍”
  * 旅行结束后缺少学习成果
  * 传统旅游 App 更偏向“去哪儿”，而不是“到了以后学什么”
* 因此童旅记重点解决：

  * **旅行前：规划**
  * **旅行中：探索**
  * **旅行后：记录与回顾**

# 四、非常重要的产品设计决策

## 4.1 “计划”和“探索任务”的关系

之前专门讨论过一个问题：

> “探索计划”和“探索任务”到底是不是两个页面？

经过讨论后，不再建议把“探索计划”单独做成一个复杂的一级导航页面。

更合理的层级是：

```text
旅行计划
  ↓
景点 / 旅行内容
  ↓
这个景点需要探索什么
  ↓
具体探索任务
```

也就是说：

**计划是任务的上一层，而不是和任务平行的独立系统。**

例如：

```text
故宫旅行计划
│
├── 午门
│   ├── 观察建筑颜色
│   ├── 寻找门钉
│   └── 了解午门作用
│
├── 太和殿
│   ├── 寻找龙纹
│   ├── 观察屋顶
│   └── 记录最喜欢的细节
│
└── 珍宝馆
    ├── 寻找特殊文物
    └── 完成观察记录
```

因此后续开发时：

**不要重新把“探索计划”设计成一个与任务完全平行的大模块。**

# 五、产品定位上的重要取舍

项目早期曾有一个右侧 AI Pet / AI 小宠物设计。

后来决定：

> **删除 AI Pet。**

原因是：

* 页面容易变得杂乱
* 会分散孩子对任务的注意力
* 当前项目的核心价值不是 AI 聊天，而是文化探索和学习记录
* UI 希望保持简单、绘本化、教育性

因此：

**后续不要重新加入 AI Pet，除非用户明确要求。**

# 二十六、Submission 的重要性

Task 与 Submission 不是一回事。


意味着：

因此数据模型应该保持：

```text

 ↓
```

而不要把：


## Implementation Environment Gate

本项目支持以下执行环境：

```text
Lenovo 本地开发环境
Codex sandbox runtime
```

不得将固定的 Windows 用户名或某个预设身份值作为项目级硬阻断。`whoami` 仅用于记录当前执行上下文；身份名称不同于历史预期时，不得仅凭此项停止任务。

开始实现或测试前，必须通过以下真实门禁：

1. `repository` 正确：当前工作目录属于童旅记目标仓库。
2. `branch` 正确：当前分支符合本次任务授权的目标分支。
3. `HEAD` 可确认：能够读取并记录当前 `git rev-parse HEAD`。
4. `workspace clean`：工作区没有未授权的修改、暂存内容或未跟踪文件。
5. `workspace writable`：当前运行时对本次授权范围内的工作区具有写入能力。

推荐检查：

```powershell
git rev-parse --show-toplevel
git branch --show-current
git rev-parse HEAD
git status --short
```

任一真实门禁失败都必须停止并报告观察到的证据与要求，不得通过更换身份、修改权限、删除锁文件或其他绕过方式继续执行。

# 三十四、真实联调应该按照什么顺序做

不要一上来全部联调。

建议：

```text
1. Login
   ↓
2. User identity
   ↓
3. Plan
   ↓
4. Task
   ↓
5. Submission
   ↓
6. Record
```

理由：

Record 是最末端的数据结果。

如果：

```text
Task
```

没有真实数据，

那么：

```text
Submission
```

无法真实创建。

如果：

```text
Submission
```

没有，

那么：

```text
Record
```
